# Bug Report: False Blurs in screenoverlay 0.6.0

**Date:** October 3, 2025  
**Reporter:** ScreenStop Production Testing  
**Severity:** HIGH - False blurs appearing without code calling show()

**✅ VERIFICATION COMPLETE:** All code is correctly synced (local source, Git, PyPI, installed venv). Everything is single-threaded 0.6.0 with NO multiprocessing. The false blur bug is NOT related to multiprocessing architecture.

## 🐛 BUG DESCRIPTION

The screenoverlay library is showing **false blurs** - the overlay appears spontaneously WITHOUT the application code calling `overlay.show()`.

### Symptoms:
- ✅ Real detections with `overlay.show()` work fine
- ❌ **Blur appears randomly during normal operation**
- ❌ No log messages showing `overlay.show()` was called
- ❌ Happens 3-4 seconds after last legitimate hide()

### Testing Environment:
- **Application:** ScreenStop Production (`/Users/user/MyProjects/screenstop/Production/`)
- **Library Version:** 0.6.0 (claimed)
- **OS:** macOS
- **Python:** 3.12

## 🔍 ROOT CAUSE ANALYSIS

After investigation, we found THE SMOKING GUN:

### 1. Version is 0.6.0 but Code is STILL Multiprocessing!
```bash
# Version check:
$ grep version /Users/user/MyProjects/ScreenOverlay/setup.py
version="0.6.0"

$ cat /Users/user/MyProjects/ScreenOverlay/screenoverlay/__init__.py

```

**BUT THE CODE STILL USES MULTIPROCESSING!**

### 2. EXACT EVIDENCE - File: `overlay.py`

**Line 12:** Still importing multiprocessing
```python
from multiprocessing import Process, Queue
```

**Lines 69-70:** Process variables still present
```python
self._process = None
self._command_queue = None
```

**Lines 118-126:** `start()` method spawns SEPARATE PROCESS
```python
def start(self):
    if self._process is not None:
        return
    
    self._command_queue = Queue()
    self._process = Process(target=self._run_process, args=(self._command_queue,), daemon=True)
    self._process.start()
    
    # Wait a bit for process to initialize
    time.sleep(0.3)
```

**Lines 128-131:** `show()` sends message to separate process via Queue
```python
def show(self):
    """Show the overlay (instant, ~1ms)"""
    if self._command_queue is not None:
        self._command_queue.put('show')
```

**Lines 146-154:** `hide()` RESTARTS THE ENTIRE PROCESS
```python
def hide(self):
    if self._command_queue is not None:
        # Hide first (instant for user)
        self._command_queue.put('hide')
        
        # Stop the process completely to prevent ghost windows
        self.stop()
        
        # Start fresh overlay for next show() (happens in background)
        self.start()  # <-- SPAWNS NEW PROCESS ON EVERY HIDE!
```

**Lines 169-179:** `_run_process()` runs in SEPARATE PROCESS
```python
def _run_process(self, command_queue):
    """Run overlay in separate process with command queue"""
    try:
        # Create windows for all monitors
        self._create_windows()
        
        # Hide all windows initially
        for win in self.windows:
            win.withdraw()
        
        # Process commands from queue
        # ... (then calls mainloop())
```

### 3. Only One Class Exists
- ❌ Only `NativeBlurOverlay` class (multiprocessing version)
- ❌ No new single-threaded `Overlay` class
- The `__init__.py` just aliases the old class: `from .overlay import NativeBlurOverlay as Overlay`

### 4. THE BUG SOURCE
The multiprocessing architecture means:
- **Main process** sends `show`/`hide` commands via Queue
- **Overlay process** receives commands and controls Tkinter
- **Race conditions** - Queue messages can arrive late/out of order
- **Ghost processes** - The separate process can become unresponsive or show spontaneously
- **No control** - Main process has NO direct access to the Tkinter window

## 💡 HYPOTHESIS

The **multiprocessing + queue communication** causes:
1. **Race conditions** between main process and overlay process
2. **Delayed queue messages** - old `show` commands arrive late
3. **Interaction with YOLO/Camera** - Something about cv2.VideoCapture or YOLO processing triggers the separate process to show
4. **Spontaneous deiconify()** - The separate Tkinter process's mainloop might be responding to system events

Implement the **single-threaded architecture** as described in `/Users/user/MyProjects/screenstop/03102025tasks.md`:

### Required Changes:

1. **Create NEW `Overlay` class** (not modify `NativeBlurOverlay`)
2. **Remove ALL multiprocessing:**
   - No `Process`, no `Queue`
   - No separate process spawning
   - No `start()` method needed

3. **Direct Tkinter in same process:**
   ```python
   class Overlay:
       def __init__(self, mode='blur', blur_strength=3, opacity=0.85, color_tint=(136, 136, 136)):
           self.root = tk.Tk()
           self.root.overrideredirect(True)
           self.root.attributes('-topmost', True)
           # ... configure window ...
           self.root.withdraw()  # Start hidden
       
       def show(self):
           self.root.deiconify()
           self.root.lift()
       
       def hide(self):
           self.root.withdraw()
       
       def update(self):
           """CRITICAL: Call this regularly in main loop!"""
           if self.root:
               self.root.update()  # Process Tkinter events without blocking
       
       def stop(self):
           if self.root:
               self.root.destroy()
   ```

4. **Update `__init__.py`:**
   ```python
   from .overlay import Overlay  # Import new single-threaded class
   __version__ = '0.6.0'
   ```
